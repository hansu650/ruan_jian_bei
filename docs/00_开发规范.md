# 开发规范

本文档用于约定 EduForge 智学工坊项目的基础协作规范。第一阶段只建立规范，后续阶段按此逐步扩展。

## 分支命名规范

- `feat/xxx`：新功能
- `fix/xxx`：问题修复
- `docs/xxx`：文档更新
- `refactor/xxx`：重构

示例：

```text
feat/profile-dialog
fix/api-health
docs/environment-guide
refactor/course-service
```

## Commit Message 建议

使用简短清晰的英文动词前缀：

```text
feat: add health check
docs: add environment guide
chore: initialize project structure
fix: repair api startup script
refactor: split course service
```

## Python 代码规范

- 使用类型注解。
- 保持函数短小，避免单个函数承担过多职责。
- 后续业务逻辑放到 `services` 或 `agents`，不要堆在入口文件。
- 后续 API 路由放到 `routers`，按业务域拆分。
- 不要在 `main.py` 堆业务；`main.py` 只负责创建 FastAPI app、注册中间件和路由。
- 新增逻辑时补充对应测试，至少覆盖关键分支和失败路径。
- 使用 `ruff` 做风格检查，使用 `mypy` 做基础类型检查。

第一阶段只允许保留 health check，不提前创建正式业务模块。

## TypeScript 代码规范

第一阶段尚未创建前端项目，但后续前端开发建议遵守：

- 使用 TypeScript，避免使用 `any` 逃避类型设计。
- 组件保持单一职责。
- 页面级组件负责组合，通用组件放到统一目录。
- API 请求层和 UI 组件分离。
- Tailwind class 保持可读，不在组件里堆大量重复样式。
- shadcn/ui 组件修改要保留可维护性，避免难以追踪的大面积复制。

## 环境变量规范

- 使用 `.env` 保存本地配置。
- 仓库只提交 `.env.example`。
- 不提交真实 `.env`。
- 新增环境变量时同步更新 `.env.example` 和相关文档。

## API Key 规范

- 不允许提交真实 API Key。
- 不允许在日志中输出 API Key。
- 不允许把 API Key 写死在源码、测试、README 或演示脚本中。
- 需要展示配置方式时，只使用占位符或空值。

## 数据文件规范

- 不提交本地 sqlite 数据库文件。
- 不提交 `.chroma` 向量库持久化目录。
- 示例课程文档后续放入 `data/sample_courses/`，需要确保可公开、可复现。
- 大文件或模型文件要先评估是否适合进入 Git 仓库。

## AI Coding 使用规范

- 可以使用 Codex 辅助生成代码、文档、测试和脚本。
- 生成后必须人工 review，确认逻辑、依赖、边界条件和安全性。
- 关键业务逻辑必须由团队确认，尤其是学习画像、智能体协作、测验评估和防幻觉策略。
- 不要让 AI 一次性生成过大变更。大功能应拆成小阶段、小 PR、小测试。
- 比赛文档中需要说明使用过的 AI Coding 工具、使用范围和团队自主开发部分。

## 提交前检查

在项目根目录执行：

```bash
python scripts/check-env.py
```

在后端目录执行：

```bash
cd apps/api
pytest
```

后续阶段可逐步加入：

```bash
ruff check .
mypy .
```

## 比赛提交注意

- 记录使用的开源依赖，包括名称、来源和协议。
- 记录使用的 AI Coding 工具和使用方式。
- 文档要说明团队自主开发部分。
- 不抄袭历届项目代码，不使用来源不明的业务代码。
- 演示视频控制在 7 分钟内，突出 A3 题面要求与 EduForge 的闭环价值。
- PPT、系统开发说明书、测试说明书和运行说明要与最终代码保持一致。
