# 关系模型

## 学习目标

学习本节后，你应该能够解释关系、元组、属性、域、主键、外键和关系模式的含义，能够把简单业务对象转换成关系表，并理解关系模型为什么强调集合、约束和运算。你还需要能初步判断一个表设计是否存在重复、歧义或引用不清的问题。

## 核心概念

关系模型用表来表达数据。表中的一行称为元组，一列称为属性，属性允许取值的范围称为域。关系模式描述表的结构，例如 Student(id, name, major, grade_level)，而关系实例是某一时刻表中的具体数据。

主键用于唯一标识表中的一行。一个好的主键应该稳定、简洁、不依赖会频繁变化的业务描述。学号常被用作学生表主键，但姓名通常不适合，因为重名很常见。外键用于表达表之间的引用关系，例如选课表中的 student_id 引用学生表，course_id 引用课程表。

关系模型的核心不是“表长得像二维表格”，而是表背后的约束和集合语义。数据库可以检查主键是否重复、外键是否引用不存在的数据，也可以用选择、投影、连接等操作从已有关系中得到新的结果。SQL 是关系模型在工程中的主要使用方式，但关系模型本身比 SQL 语法更基础。

## 示例说明

以学习平台为例，如果把学生姓名、课程名称、知识点标题、掌握度都放进一张大表，短期看似简单，长期会出现重复和不一致。某门课程改名后，需要修改很多行；同一个知识点被多个学生引用时，知识点描述会被重复保存；如果某个学生暂时没有测验记录，可能还无法表示这个学生存在。

更好的方式是拆成 Student、Course、KnowledgePoint、ProfileDraft 等表。Student 保存学生自身信息，Course 保存课程信息，KnowledgePoint 保存某门课程下的知识点，ProfileDraft 保存学生与课程相关的学习目标、薄弱点和偏好。不同表通过 id 建立引用。这样既减少重复，也让后续查询更清晰。

## 常见误区

不要把外键理解成“字段名字相同”。真正的外键是数据库层面或设计层面的引用约束。另一个误区是认为表拆得越细越专业。表拆分要服务于数据含义和更新需求，过度拆分会让查询复杂，过度合并又会导致重复和异常。还有同学会把一列塞入多个含义，例如在一个字段里写“计算机-大二-男”，这会让查询和约束都变困难。

## 练习提示

请为选课场景设计 Student、Course、Enrollment 三张表，并标出主键和外键。思考如果一个学生可以选多门课，一门课也可以被多个学生选择，那么为什么不能只在 Student 表里加一个 course_name 字段？再尝试写出“查询某学生已选课程”的自然语言过程。
