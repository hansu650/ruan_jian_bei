# 查询优化

## 学习目标

学习本节后，你应该能够理解查询优化的基本目标，知道数据库会根据统计信息、索引和执行计划选择访问路径，能从表扫描、索引扫描、连接顺序、过滤条件和返回列等角度分析简单 SQL 的性能问题。

## 核心概念

查询优化是数据库把声明式 SQL 转换为较高效执行方案的过程。同一条 SQL 可以有不同执行方式：先过滤再连接，还是先连接再过滤；使用索引查找，还是全表扫描；先读取小表，还是先读取大表。优化器会根据统计信息估计成本，然后选择它认为更合适的计划。

执行计划是观察查询行为的重要工具。虽然不同数据库显示格式不同，但通常会展示访问方式、使用的索引、扫描行数、连接方式和排序操作。开发者不需要手写底层算法，但需要写出便于优化器理解的 SQL，并建立合理索引。

优化并不等于盲目改写 SQL。第一步应确认业务需要哪些数据，减少不必要列和不必要行；第二步查看过滤条件和连接条件是否清晰；第三步检查索引是否匹配常见查询；第四步再考虑缓存、冗余字段或结构调整。

## 示例说明

在知识库检索页面中，如果每次搜索都读取所有文档和所有 chunk，数据量大后会变慢。第四阶段先实现简单关键词检索，是为了保证链路清晰；后续可以逐步加入全文索引、向量检索或混合检索。即使未来加入 RAG，查询优化仍然重要，因为检索阶段决定了大模型能看到哪些上下文。

另一个例子是课程知识点列表。如果总是按 course_id 查询，并按 order_index 排序，那么相关索引可以帮助数据库更快定位和排序。若接口只需要 title、chapter、difficulty，就不必把大段 summary 或正文内容全部返回。

## 常见误区

常见误区是只在慢了以后才考虑数据访问方式。更好的做法是在设计表和接口时就知道主要查询路径。另一个误区是过早优化，把简单系统做得很复杂。本项目第四阶段故意不引入 ChromaDB 和 embedding，就是为了先验证文档解析、分块、入库、来源展示这条主链路。

还有同学会把“SQL 写得短”当成“性能好”。短 SQL 可能隐藏复杂子查询，长 SQL 也可能因为条件清晰而更容易优化。性能判断应基于数据规模、执行计划和实际耗时，而不是凭语感。

## 练习提示

请选择一个接口，例如“查询某课程所有知识点”，思考它的主要过滤条件、排序字段和返回字段。再思考如果课程资料 chunk 达到 10 万条，关键词检索可能遇到哪些瓶颈，后续可以用哪些技术逐步优化。
